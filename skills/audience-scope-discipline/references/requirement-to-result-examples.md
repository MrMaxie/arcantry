# Requirement to Result Examples

Use this reference when requirements or source material could be copied into reader-facing output. Each requirement below states the audience task or source evidence that admits the detail. The good result is one valid outcome, not a template. Do not reuse its fields, controls or wording unless the actual source requires them.

## Interface and product copy

### First-contact setup

- Requirement: A first-time visitor must select the local folder the tool will inspect.
- Good result: "Choose the folder you want to inspect." with a "Choose folder" action.
- Bad result: "Configure this project context."

### Established product terms

- Requirement: The product already calls an action "Sign in" and its destination "Workspace".
- Good result: Preserve those established names in the relevant controls.
- Bad result: Replace them with a descriptive slogan and explain concepts the audience already knows.

### Primary-object view

- Requirement: Staff must identify the primary record, see the current state needed for their decision and open settings for an optional integration.
- Good result: Keep only source-established identification and decision fields visible, with one clear action for the integration settings.
- Bad result: Let every available integration metric and repeated settings label dominate the primary record.

### Visible state change

- Requirement: The interface visibly switches from an editor to its rendered preview.
- Good result: Let the visible transition and accessible selected state communicate the change.
- Bad result: Add step labels that repeat what the interface already shows.

### Expert controls

- Requirement: An experienced user must tune the output through established controls whose distinct effects are supported by product evidence.
- Good result: Keep one compact panel containing the proven controls under their established names.
- Bad result: Expose every implementation parameter, redundant control and internal processing term.

## Documentation and answers

### Quick start

- Requirement: A developer needs to start the tool for an arbitrary local command.
- Good result: Show the shortest established command and one sentence describing its observable result.
- Bad result: Explain the transport, process model, environment variables and internal endpoint before showing how to start.

### Client answer

- Requirement: A client asks whether a capability exists. Current product evidence and an accepted plan describe different states.
- Good result: Answer the question directly and label current and planned behavior separately.
- Bad result: Narrate the investigation, merge planned behavior into the present or invent a delivery estimate.

### Public profile

- Requirement: A public profile must explain the person's work using verified projects and outcomes.
- Good result: Use concrete work and outcomes supported by the source material.
- Bad result: Substitute generic slogans, invented metrics or decorative interfaces for evidence.

## Boundaries, diagnostics and exactness

### Public and private products

- Requirement: A reusable public component is derived from a private product.
- Good result: Publish only portable interfaces and neutral examples supported by the public contract. Keep private identity, endpoints, assets and workstation values outside it.
- Bad result: Copy private or local values into public material merely to make an example concrete.

### Exact verification

- Requirement: A verification procedure names the evidence a reviewer must compare.
- Good result: Show the exact source-backed values required by that procedure in a copyable form.
- Bad result: Replace them with a generic assurance or invent additional evidence types.

### Recoverable error

- Requirement: An end user can perform a stated recovery action. A support reference is available only when an established support path accepts it.
- Good result: State what happened, provide the available recovery action and include the reference only when the stated support path can use it.
- Bad result: Show raw protocol, stack or trace details, omit a usable support reference, or invent a fallback that the audience cannot perform.
