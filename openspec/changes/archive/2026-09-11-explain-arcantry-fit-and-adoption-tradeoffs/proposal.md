# Why

Arcantry's overview introduces its source names and internal model before a new evaluator can recognize the project problems it addresses. Technical and organizational evaluators also lack one decision-oriented account of adoption effort, ongoing ownership, pilot success and how Arcantry fits alongside disciplined ADR, RFC, issue, documentation and release practices. Adoption guidance does not state clearly enough that shared project-work configuration is separate from product runtime, build, CI and publication integration.

# What changes

- Lead product evaluation with recognizable repository problems, user outcomes and concrete examples before Arcantry terminology.
- Explain evaluation cost, adoption effort, ongoing responsibilities, pilot success and stopping criteria without unsupported return-on-investment claims.
- Define how Arcantry complements mature decision, planning, documentation and release practices, including non-goals and cases where adoption adds little value.
- Distinguish shared project-work configuration from product runtime, build, CI and publication integration, which remain separately selected adoption decisions.
- Preserve deeper technical detail for readers who need to inspect the source model and contracts.

# Out of scope

- Replacing ADR, RFC, issue tracking or repository documentation.
- Claiming universal productivity or financial returns.
- Changing adoption or runtime behavior.
